* Think about a better syntax for the `entrypoint!` macro.  One common use case
  that I want to support would be to parse accounts and instruction bytes, and
  immediately invoke a function with a name derived from the instruction.

  This is already partially implemented, as the macro now allows you to skip the
  branch body.  In which case it inserts a call to a function that has the name
  derived from the instruction name.  But with the current closure like syntax,
  one still has to provide names for accounts and instruction items.

  These names are not used by the user code.  So they seem redundant from the
  user standpoint.

  One option is to move from the closure syntax to something that is similar to
  the enum destructuring syntax.  Something like:

  ```rust
    Instruction::Setup(metadata: NewAccountMut<Metadata>; admin: &Pubkey),
    Instruction::CreateUser {
        metadata: &OwnAccount<Metadata>,
        new_user: NewAccountMut<User>,
        ;
        name: &str,
    },
  ```

  One slight problem is that the enum element is now not a complete match
  pattern.  So something like this is no longer possible:

  ```rust
    inst @ [Instruction::ForwardFrom..Instruction::ForwardTo] => |
      accounts: Vec<SharedAccountRef>,
      ;
      data: &[u8],
    | => forward(inst, accounts, data),
  ```

  Similarly, if the `Instruction` enum variants has any internal values, it
  becomes impossible to access them.

  Maybe that is OK?  The main focus should be the common use case when
  instructions are defined as a list of indices.  It is not very likely that an
  index type would actually need to do complex parsing.

  Another alternative would be to provide two macros that parse different
  syntax?  But this seems a bit too complex.

  One suggestion from discussion with Sam is to describe instruction processing
  as an implementation of a trait:

```rust
enum Instruction {
    Setup = 1,
    CreateUser = 2,
    SetUserName = 3,
    StakeTo = 4,
    RecordAction = 5,
    ComplexOp = 6,
}

#[entrypoint]
impl ProgramEntrypoint for Instruction {
    #[value(Instruction::Setup)]
    fn setup(
        program_id: Keypair,
        Accounts {
            metadata,
            staker,
            target_user,
        }: Accounts {
            metadata: &OwnAccount<Metadata>,
            staker: OwnAccountMut<Staker>,
            target_user: &AnyAccount<User>,
        },
        DataParsers {
            amount,
        }: DataParsers {
            amount: u64,
        },
    ) {
        /* ... */
    }
}
```

  `entrypoint` is applied to a trait implementation.

  Individual instruction handlers are provided as functions.

  The `Accounts` and `DataParsers` are "fake types" - they do not really exist,
  but just provide structure that the macro reads.

  Compared to the current macro it is pretty verbose.  In particular, the
  account names need to be repeated twice.

  Another idea is to describe instructions as part of the enum that defines the
  instruction code:

```rust
enum InstructionEnum {
    Setup {
        accounts: (/* metadata: */ NewAccountMut<Metadata>),
        data: (/* admin: */ Pubkey),
    }
}
```

  There is a number of open questions related to this approach.  It seems to be
  rather verbose.  And there is a problem of moving the information from the
  enum into the parser generation macro.

  There are some smart hacks that allow macros to share data across modules.
  Sam actually figured out a few interesting approaches.  But they suffer from
  usability restrictions in edge cases, which makes it a worse option as a
  rather fundamental building block.  Still it might make sense to write down
  options with examples for comparison.

* Support full deserialization/serialization of account data, rather than using
  references.  While it is slower for large accounts, it is possible that the
  program needs to operate on an smaller account defined by an existing struct,
  not designed for direct access.  Would it be a viable use case?

  If account struct is written in such a way that it can change it's layout and
  possible also size, full deserialization/serialization cycle could also be a
  viable alternative.

  There are some interesting ideas as to how this can be implemented.  In
  particular, I think, it might be possible to create "guards" that are
  constructed from account pointers similar to `Account` type and friends, that
  would produce a deserialized version of the account.  The trick is that
  "guards" can not be destroyed until an account object of an appropriate type
  is provided to them.  At which point the do deserialization, storing updated
  account data.

  I this the above may provide for a nice API, that would both guide the user
  towards a program structure with no faults, and, at the same time, would not
  hinder the users too much.

  Additional complexity here is that when an error is triggered, no data should
  be stored.  And yet, guards need to be destructed somehow.
  One solution I was thinking about is to use a type level key-value store,
  storing account objects.
  Guards would essentially require this key-value store in order to destroy
  themselves.  They consume an account object that matches their account index
  (and type) and return a store without this particular element.

  This way, it would be possible to both check at compile time that all the
  guards are getting the account objects they need, short circuit the error
  propagation case, and not require users to provide accounts in any particular
  order, as long as they provide all of them.  It should probably be possible to
  generate decent errors, indicating which exactly account object is missing.

* Split `entrypoint!` into several parts:
  1. A `macro_rules!` macro that generates a program entrypoint function and
     the wrapper that converts `Result<(), ProgramError>` into `u64`.  Wrapper
     then calls the next macro.

     It takes the program account description and just forwards it.

  2. A `macro_rules!` macro that invokes `entrypoint_v2::parse_program_input()`,
     allocates state for the output on the stack and invokes the next macro with
     all of these.

     It takes the program account description and just forwards it.

  3. A macro that produces a parser to parse accounts and instruction data,
     following the provided program account description.

  This kind of split could help people understand the parsing structure without
  looking at the proc-macro that generates the parser.

  It will also provide better setup for testing.

  Next it would be great to consider how account and instruction data parsers
  can be augmented with arbitrary user logic.  For example, if the account list
  need to be processed differently, depending in the instruction data, it would
  be nice if an `if` statement can be added, rather than requiring custom DSL.

  One idea would be to provide a macro that runs the accounts parser and/or a
  macro that runs the data parser, referencing a common "parsing context".

  One problem is that duplicate reference mask is constructed using information
  from all accounts.  Similarly, stack state allocation is based on the number
  of provided accounts.

  It is not entirely clear to me, how the above can all be combined to produce a
  good solution yet.

  == Reasoning for not following the original plan

  Fernando pointed out that in certain cases, in particular with CPI calls,
  additional accounts need to be provided in order to satisfy the "total SOL
  balance does not change over an invocation" condition.  As a result, even a
  program that has a well specified list of accounts might end up being called
  with additional accounts at the end as part of a more complex CPI invocation.

  So, by default, we have to ignore any trailing accounts.  And this is also the
  current default for most(?) frameworks and programs.

  It would be great to double check this, and write a doc-comment clarify this
  decision with appropriate details.

* Add a notion of a "reference mask" - when account references are considered, a
  mask is provided that tells the parser which accounts references can point at.
  This mask is produced by checking instance of the `CanReference` trait that
  indicates if two account types can reference each other.

  It seems like a somewhat fragile system.  But I could not figure out a
  different approach to making sure that `&Account<T>` and `&SharedAccountRef`
  would not reference each other.

  As for mutable accounts the mask will cover all the provided accounts, mask
  check replaces the check for the reference value to be `u8::MAX`, I think?

  I've also considered an alternative approach, where an account would declare
  to be in a particular "account check kind" - like a type of account types.
  Only accounts of the same kind can be referencing the same account.
  `&Account<T>` and `&mut Account<T>` are "statically checked kind", while
  `SharedAccountRef` is a "runtime checked kind".

  Kind can be expressed as either as a bit or as a byte value.  And the parser
  will have an array of account kinds for all the accounts parsed so far.  Any
  account that is a reference would need to be of the same kind as the account
  it is pointing at.

  Using a byte is more extensible, allowing users to define their own checking
  rules, separate from the ones provided by the library.

  Need to think about the `AnyAccount` here.  Will there be `&AnyAccount`, `&mut
  AnyAccount` and `SharedAnyAccountRef`?  Or will there be just the
  `&AnyAccount` one?  If it is the latter, it could be impossible to express the
  right checks with regard to "account check kind" if the kind check is just a
  simple comparison for equality.

  Maybe checks can be expressed as some `IsCompatible` trait or something like
  that?  Similar to `PartialEq`, it might provide more flexibility in
  determining which account types can work with each other?

  Another idea on how this check can be implemented at the very low level is to
  augment each account with a bit mask, that indicates which other indices are
  blocked (or allowed) to be referenced.  Making the verification a bit shift,
  followed by a bit check.  There is still a question as to how this mask should
  be generated in each particular case.  Macro has limited capabilities here, as
  it can not see inside of the provided types.  Maybe the bit mask can be
  computed by const functions provided by different account types?  This may
  provide quite a lot of flexibility and allow for extensibility as well.
